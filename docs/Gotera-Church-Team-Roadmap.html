01 · Executive summary

Current position

We have completed the first public-facing frontend direction and stabilized the basic CI workflow. The project is now ready to move from visual foundation into product integration: connecting the church website to a reliable Laravel API and building the private management system behind it.

One-sentence status: The public website experience is in place; the backend domain features, authentication, data workflows, and frontend-to-API integration are the main work remaining.
Complete Public frontend foundationResponsive Gotera Church landing page, real church photos, video hero, bilingual English/Amharic UI, events, service cards, gallery, contact/visit modal, and responsive navigation.
Complete CI baselineGitHub Actions runs quality, backend, and frontend jobs. The repository-level CodeQL/SARIF blockers were removed from the current pipeline.
Next Backend foundationFinish models, migrations, validation, authentication, API resources, and tests for members before adding the other management features.
Next Product integrationReplace frontend placeholder content with API-backed events, announcements, appointment requests, and a secure admin dashboard.

Project goal

Replace the church’s Excel-based member management with a centralized system for member records, contributions, participation, builder history, events, announcements, appointments, reporting, and English/Amharic support.

  • Real church memories integrated from the Telegram photo folder: procession, community, clergy, young servants, and gathering photos.
  • First-page hero video added from IMG_3048.MOV, converted to a browser-compatible, muted 30-second MP4 loop with a poster fallback.

  • Interactive “Plan a visit” form with confirmation state; currently frontend-only and not yet connected to Laravel.
  • Mobile navigation, responsive grids, keyboard-friendly buttons, labels, alt text, and semantic sections.

Repository and CI delivery

  • Frontend is React + Vite and passes ESLint and production build.
  • Backend is Laravel with PHPUnit scaffolding, MySQL service configuration, Sanctum dependency, and migrations.
  • CI workflow is scoped to code quality, backend tests, and frontend tests/build.
  • CodeQL and SARIF/Trivy upload jobs are currently removed to avoid repository permissions and code-scanning configuration failures. Security scanning can be reintroduced after GitHub repository settings are ready.
Verified locally: pnpm run lint, pnpm run build, and git diff --check pass for the frontend.

Important boundary

The current frontend is a polished public UI prototype. Its content is mostly static. The visit form does not yet save to the backend, and the management dashboard is not yet implemented.

04 · Roadmap

Recommended delivery sequence

Phase 1 · Backend foundation and member management Priority 1

Agree on schema and roles. Implement Member CRUD, duplicate prevention, search, pagination, validation, API resources, policies, factories, seed data, and feature tests. Add the first admin member list and member detail screens.

Phase 2 · Public content API and frontend integration Priority 2

Implement events, announcements, church information, and appointment request endpoints. Replace static event cards and the visit modal with API data. Add loading, empty, error, and success states.

Phase 3 · Authentication and administration Priority 3

Build login, logout, session handling, admin layout, role-based navigation, and protected routes. Add administrator and priest permissions; priests must not see sensitive contribution data.

Phase 4 · Contributions and participation Priority 4

Add contribution records, payment method, monthly summaries, attendance, and activity participation. Include data validation, auditability, filtering, and safe export rules.

Phase 5 · Builder history, reports, and launch readiness Priority 5

Implement 10-month builder qualification/history, dashboards, CSV/PDF exports, backups, production environment variables, logging, monitoring, accessibility review, and security scan reintroduction.

05 · Team execution guide

Main frontend tasks

  1. Create a typed API client and one shared request/error pattern.
  2. Build the authenticated admin shell: sidebar, top bar, breadcrumbs, responsive behavior.
  3. Build members list, search/filter, create/edit form, detail view, and delete confirmation.
  4. Connect public events, announcements, and appointment form to backend endpoints.
  5. Add loading skeletons, empty states, validation messages, toast feedback, and network-error recovery.
  6. Keep English/Amharic translations in one source; do not hardcode user-facing strings in feature components.
  7. Add frontend tests for language switching, form validation, route protection, and key UI states.

Main backend tasks

  1. Document API contracts before implementation: URL, method, request, response, validation errors, auth.
  2. Complete Member model/migration with unique identifiers, indexes, soft-delete decision, and audit fields.
  3. Implement Form Requests, API Resources, policies, service layer, controller actions, and tests.
  4. Define roles: administrator, priest/view-only, and public visitor. Protect sensitive routes explicitly.
  5. Implement events, announcements, and appointment requests as the next public-facing vertical slice.
  6. Add factories/seeders so every developer and CI job can create deterministic demo data.
  7. Use database transactions for multi-record writes and consistent JSON error responses.

Team working rules

One feature per branch

Use feature/member-management, feature/events-api, or fix/.... Open pull requests into develop.

Small pull requests

Keep a PR focused on one vertical slice. Include screenshots for UI work and endpoint examples for API work.

Definition of done

Code, validation, tests, responsive behavior, bilingual text, error state, documentation, and CI passing.

Never commit secrets

Use .env locally, environment secrets in GitHub, and sanitized demo data only.

Before production: restore a security scan only after enabling GitHub code scanning/security events, add rate limiting and request protection, review permissions, configure backups, and remove placeholder contact/event data.
